# 概念的要件定義書 - fred_provider

## 1. サービス概要
`fred_provider` は、セントルイス連邦準備銀行（FRED）が提供する経済統計データを収集、保存、および提供するためのマイクロサービスです。`ayato-finance-ecosystem` におけるデータ供給レイヤーの一部として機能します。

## 2. 実装対象とその根拠（Why）

### 2.1 FRED API による自動収集
- **内容**: `fredapi` ライブラリを使用し、指定されたシンボルの時系列データを定期的に取得する。
- **根拠**: 手動のデータ取得を排除し、最新の経済指標（金利、失業率等）を常にエコシステム内で利用可能にするため。

### 2.2 DuckDB によるローカル永続化
- **内容**: 収集したデータを DuckDB 形式で `data/` ディレクトリに保存する。
- **根拠**:
    - **OLAP性能**: 時系列データの分析クエリに対して非常に高速。
    - **ポータビリティ**: 単一のファイルとして管理でき、バックアップや移動が容易。
    - **サーバーレス**: 外部の DB サーバー（PostgreSQL 等）を構築する運用負荷を避け、プロバイダー単体での完結性を高める。

### 2.3 FastAPI によるデータ提供 API
- **内容**: 他のサービスがデータを取得するための RESTful エンドポイントを公開する。
- **根拠**: エコシステム内の他のサービス（分析エンジン、可視化ツール等）が、DB 構造を意識せずに標準的なプロトコルでデータにアクセスできるようにするため。

### 2.4 Master DB への登録・連携
- **内容**: 自身のステータスや保持しているデータ量を Master DB に通知する。
- **根拠**: エコシステム全体でのサービスディスカバリを実現し、どのデータがどのプロバイダーに存在するかを中央管理するため。

### 2.5 キューベースの書き込み処理
- **内容**: 収集（Collector）と書き込み（Writer）を分離し、スレッド間のキューを介して非同期に処理する。
- **根拠**: API 取得の待ち時間が DB 書き込みをブロッキングするのを防ぎ、効率的なデータ ingestion を実現するため。

---

## 3. 非実装対象とその根拠（Why not）

### 3.1 リアルタイム・ストリーミング（WebSocket）
- **根拠**: FRED が提供するマクロ経済指標は、更新頻度が日次、月次、四半期ベースであり、秒単位のリアルタイム性は不要。ポーリングまたは定期実行（Sync）で十分な鮮度を維持できるため。

### 3.2 複雑なデータ変換（ETL/加工）
- **根拠**: 本サービスの責務は「データの提供（Provider）」に限定する。複雑な計算や派生指標の作成は、後続の分析サービス（Analyzer）で行うことで、単一責任の原則を維持し、再利用性を高めるため。

### 3.3 サービス単体での高度な認証・認可
- **根拠**: 本サービスはエコシステム内での利用を前提とした内部サービスである。セキュリティ境界はゲートウェイまたはネットワークレベルで担保し、サービス内部での実装オーバーヘッドを削減するため。

### 3.4 分散型データベース（PostgreSQL/MySQL等）への保存
- **根拠**: 1プロバイダーが扱うデータ量は DuckDB で十分に処理可能な範囲である。分散 DB の採用はインフラの複雑性を増大させ、プロバイダーの「軽量・交換可能」という特性を損なうため。

## 4. 技術選定の方針

| 技術 | 役割 | 選定理由 |
| :--- | :--- | :--- |
| **Python 3.12** | 開発言語 | エコシステム全体の標準。豊富なデータ解析ライブラリ。 |
| **DuckDB** | データベース | 分析性能、管理の容易さ、ファイルベース。 |
| **FastAPI** | Webフレームワーク | 型安全性、高速なパフォーマンス、自動ドキュメント生成。 |
| **Loguru** | ロギング | 構造化ログと直感的な API による保守性向上。 |
| **Pydantic Settings** | 設定管理 | 環境変数ベースの堅牢な設定管理。 |

---

## 5. 設計思想
- **Stateless API**: API 自体は状態を持たず、データは DuckDB に集約する。
- **Modular Ingestion**: Collector と Writer を疎結合に保ち、将来的なデータソース拡張を容易にする。
- **Registration-First**: Master DB への登録を必須とし、エコシステムへの参加を自動化する。
