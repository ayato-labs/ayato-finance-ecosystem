# トラブルシューティング：Gemma 4 モデルにおけるエンコーディングと性能上の課題

本ドキュメントでは、金融ナラティブ抽出エンジン（Gemma 4 採用）の開発中に発生した主要なトラブルとその解決策を記録します。

## 1. 日本語プロンプトの文字化けとLLMのハング

### 事象
Windows環境のターミナルからPythonスクリプトを実行した際、LLMに送信するプロンプト内の日本語が文字化けし、モデルからのレスポンスが永遠に返ってこない（ハングする）現象が発生した。

### 原因
- **エンコーディングの不一致**: UTF-8で記述されたスクリプト内の日本語文字列が、Windowsの標準エンコーディング（CP932/Shift-JIS）と干渉し、LLMへのリクエスト時に不正なバイト列として送信されていた。
- **モデルの挙動**: Gemma 4 などのモデルは、入力に不正な文字コードが含まれると、エラーを返さずに無限ループに陥るか、極端に長い推論時間を要する特性があることが示唆された。

### 解決策
- プロンプトのデバッグ時に `repr()` を使用して不可視文字や文字化けを可視化するようにした。
- スクリプトの実行環境（ターミナル）のエンコーディングをUTF-8に固定するか、重要なプロンプトについては英語での記述を併用する方針とした。

## 2. PascalCase（大文字区切り）の単語リストによる処理遅延

### 事象
EDINETのタグ名（例: `DocumentTitleCoverPage`）を100個以上リストとして渡すと、モデルが「思考（Thinking）」に数分以上要するか、タイムアウトする現象が発生した。

### 原因
- **トークナイズの負荷**: スペースのない長い英単語の羅列は、モデルのトークナイザーにとって解析負荷が高く、アテンション機構において不必要な計算コストを増大させていた。

### 解決策
- **PascalCaseの分割**: 正規表現を用いて `DocumentTitleCoverPage` → `Document Title Cover Page` のようにスペースを挿入する前処理を導入した。
- **結果**: トークナイズが効率化され、モデルの理解精度とレスポンス速度が劇的に向上した。

## 3. Gemma 4 における SDK 機能の互換性

### 事象
`google-genai` SDK の `response_mime_type="application/json"` や `system_instruction` を使用すると、正常に応答が得られないケースがあった。

### 原因
- Gemma 4 は公式にはこれらをサポートしているが、SDK のバージョンや実行環境によっては、Gemini 固有の機能として扱われ、非互換が発生する場合がある。

### 解決策
- **手動パースへの切り替え**: `response_mime_type` に頼らず、プロンプト内で「JSON形式で回答せよ」と指示し、出力から正規表現でJSONブロックを抜き出す堅牢なパースロジックを実装した。
- **思考プロセスの強制**: プロンプト冒頭に「まず思考（Thinking）せよ」と記述することで、モデルの推論能力を最大限に引き出しつつ、最終的なJSON出力を安定させた。
