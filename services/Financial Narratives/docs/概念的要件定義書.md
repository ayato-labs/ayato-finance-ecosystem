# Financial Narratives - Implementation Plan

## Project Overview
`Financial Narratives` は、企業の公式開示書類(有価証券報告書、決算短信、10-K, 10-Q 等)から、意思決定に直結する**定性情報(テキストデータ)**を専門に取得・構造化して提供する API サーバーである。
`Financial Figures`(数値データ)と対になり、企業の「数字」の背景にある「物語と規律」を明らかにする。
分析は、このシステムのAPIサーバーを呼び出して使用しているシステムが担う役割であって、このシステムはデータベースの構築とAPIの提供までを行う

## Target Documents
- **Japan**: EDINET (有価証券報告書、四半期報告書), 決算短信 (TDnet)
- **US**: SEC EDGAR (10-K, 10-Q)

## Focused Extraction Areas (Scope)
意思決定支援、特に DCF モデルの精度向上と企業の質(ガバナンス、成長性)判定に特化する。

### 1. 投資・成長の見通し (Investment & Growth)
- **設備投資 (Capex)**: 将来の投資計画、既存設備の更新予定、投資の意図。
- **研究開発 (R&D)**: 重点研究項目、技術的優位性の説明、将来の成長エンジンの特定。

### 2. ガバナンスと規律 (Governance & Discipline)
- **資本配分の方針**: キャッシュの使い道に関する経営者のコミットメント。
- **ガバナンス体制**: 取締役会の構成、役員報酬の設計(インセンティブ)とその選任理由。
- **政策保有株式**: いわゆる「持ち合い株」の保有合理性と削減方針。

### 3. リソースと基盤 (Resources & Foundations)
- **従業員の状況**: セグメント別の人数、平均年収、勤続年数（企業の持続可能性の指標）。
- **研究開発・設備投資**: ニュースリリースでは見えない長期的な投資計画と進捗。

## Why Official Filings (XBRL) over News?
ニュースメディアやプレスリリースでは代替できない、公式書類（有価証券報告書等）にこだわる理由は以下の通り。

1. **法的責任に伴う信頼性**: 虚偽記載に罰則がある公式書類は、企業の「不都合な真実」も隠さず記載される唯一のソースである。
2. **網羅性と詳細度**: ニュースは「話題性」に左右されるが、公式書類は法に基づき「地味だが重要な情報」をすべて網羅する。
3. **構造的比較可能性**: 全社共通のXBRLタグにより、10年前との比較や、同業他社との「リンゴとリンゴの比較」が機械的に可能となる。
4. **情報の永続性**: メディア記事は消える可能性があるが、公式書類はアーカイブされ、企業の歴史的文脈を追跡できる。

## Information Acquisition Priority
情報の抽出・構造化は以下の優先順位で行う。

### 優先度 1 (最優先・安定稼働目標)
- **設備投資 (Capital Expenditures)**
- **研究開発費 (R&D Activities)**
- **ガバナンス (Corporate Governance)**
これらのナラティブを安定して抽出し、時系列で構造化データ化できる状態を第一のゴールとする。

### 優先度 2 (ニュースでは代替不可能な詳細情報)
- **従業員の状況**: 平均給与、勤続年数等（数値を含むテキストブロック）。
- **役員報酬と選任理由**: 個別の報酬額および、なぜその人物が選ばれたのかという定性ロジック。
- **政策保有株式**: 持ち合い株の具体的な銘柄と保有目的、削減状況。

## Architecture & Orchestration (アーキテクチャとオーケストレーション)

本システムは、ネットワークI/Oが支配的な「データ取得フェーズ」と、API推論時間が支配的な「LLM構造化フェーズ」のボトルネックを完全に分離するため、**「状態駆動型オーケストレーション（State-Based Orchestration）」**を採用している。システムは「Data Plane（実データ）」と「Control Plane（状態管理）」の2つの層で構成される。

### 1. Data Plane: 分散・用途別データストア (DuckDB)
実データ（巨大なテキストやJSON）を保存する高速なOLAPレイヤー。DuckDBのシングルライター制限による競合を防ぐため、市場ごとに物理ファイルを分離している。

- **Qualitative Data Lake (`filings` テーブル)**: 
    - **原則**: 「拾えるものはすべて拾う」。Ingestion段階でのフィルタリングを一切排除し、全ての`ix:nonNumeric`タグを「キー・バリュー」として無差別・全量保存する。
    - **目的**: 網羅性の完全担保。パースエラー時も装飾を捨てて生テキストを死守する。
- **Structured Fact Store (`structured_data` テーブル)**:
    - **役割**: LLMを用いてData Lakeから特定の「事実（Facts）」を抽出し、正規化（JSON化）した形式で保存。
    - **目的**: 意思決定支援（DCFモデルへの入力等）の即時利用。

### 2. Control Plane: マスタージョブ管理 (SQLite)
DuckDBの代わりにトランザクション（行単位の更新）に強いSQLiteをハブとして採用し、パイプライン全体の状態を管理する。

- **Sync Master DB (`data/sync_master.sqlite`)**:
    - 全ドキュメントの処理ステータス（`PENDING`, `PROCESSING`, `COMPLETED`, `FAILED`）をアトミックに管理するタスクキュー。
    - LLMの失敗時の「リトライ回数」や「エラー理由」を記録し、オブザーバビリティ（可観測性）を提供する。

### 3. State-Based Orchestration Pipeline (状態駆動型パイプライン)
パイプラインは以下の3つの独立したコンポーネント（Producer-Consumerモデル）によって自律的に稼働する。

1. **Ingestion (Producer)**:
   - 日米の当局API（EDINET/EDGAR）を並列で叩き、最速でドキュメントをダウンロード・パースして Data Lake に保存する。LLMのレイテンシには一切影響されない。
2. **Reconciler (調停者)**:
   - Data Lake と Structured DB の差分（Delta）を計算し、「取得済みだが構造化されていない書類」を検知してマスターDBに `PENDING` ジョブとして登録する。
   - 過去の構造化データを意図的に削除した場合でも、次回のReconcile時に自動検知して自己修復（再計算）を開始する。
3. **Parallel LLM Workers (Consumer)**:
   - マスターDBから `PENDING` のタスクをアトミック（重複なく）に取得し、指定された並列数（例: 10 concurrent tasks）でGemini APIに投げ続ける非同期ワーカー群。
   - 一部のタスクが致命的なエラー（Poison Pill）でクラッシュしても、マスターDB上で `FAILED` として隔離され、他のワーカーは安全に処理を継続する。

## データベース管理ルール (Database Management Rules)
本プロジェクトでは、データの信頼性と保守性を担保するため、以下の5つの原則を遵守する。

### 1. SSoT (Single Source of Truth)
- データベースの構造定義は `src/db/schema.py` を唯一の正解とする。
- コード、ドキュメント、実際のDBスキーマはすべてこの定義から派生・同期させる。

### 2. Schema-as-Code (コードとしてのスキーマ)
- スキーマ定義は Python のデータ構造として記述し、Git で管理する。
- DDL（CREATE TABLE 等）を手動で実行することを禁止し、必ずコードから生成された SQL を使用する。

### 3. バージョン管理（マイグレーション）
- `schema_migrations` テーブルを用いて、DBのスキーマバージョンを厳密に管理する。
- 変更は `src/db/migrations.py` を通じて段階的に適用し、常に再現可能な状態を維持する。

### 4. データコントラクト (Data Contract)
- 外部 API として公開するデータ構造は「契約」とみなし、破壊的変更を行う場合はバージョンアップと移行期間の確保を必須とする。
- 下流システム（`Intrinsic Value` 評価エンジン等）が期待するデータ型と意味論を保証する。

### 5. 自動ドキュメント生成 (Automated Documentation)
- `src/db/schema.py` の定義から、Markdown 形式のドキュメント（`docs/db_schema.md`）を自動生成する。
- 「ドキュメントの腐敗」を防ぎ、開発者が常に最新の仕様を確認できる環境を提供する。

## Future Considerations (Out of Scope)
- **取得時の書類・項目フィルタリング**: 唯一の例外である「テキスト情報への特化」を除き、Ingestion 段階での書類選別を禁止する。
- **数値情報の管理**: 本システムは定性情報（Narratives）に特化するため、財務諸表の数値データそのものは管理対象外とする（別システムとの連携を前提とする）。
- 一般的な「事業等のリスク」セクション(ニュース API で代替可能なため保留)。
- リアルタイム・ニュース解析(専門のニュース API に任せる)。
