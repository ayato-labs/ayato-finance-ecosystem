# 概念的要件定義書 - yfinance_provider

## 1. 背景・目的
本サービスは、`yfinance` を通じて米国株等の定性情報（企業概要、セクター等）および時系列データ（株価、財務諸表）を収集し、エコシステム内の他のサービスに提供することを目的とする。

## 2. 定性情報の履歴管理（SCD Type 2）
定性情報（事業内容やセクターなど）の変更を検知するため、ハッシュ値を用いた履歴管理（Slowly Changing Dimension Type 2 風）を導入する。
- 取得した定性情報の重要フィールド（`longName`, `sector`, `industry`, `longBusinessSummary` 等）からハッシュ値を計算。
- 前回のハッシュ値と異なる場合、または新規銘柄の場合は、履歴リストに新しいエントリ（`valid_from`, `hash`, データ本体）を追加する。
- 同一の文章を重複して保存することを防ぎ、変更があった期間を特定可能にする。

## 3. 「時間軸」に関する重要な制約（過去データの非対称性）
本システムにおける定性情報の履歴管理には、以下の「時間軸」に関する重要な制約が存在する。

### 3.1 今から未来の情報は保存できるが、過去の情報は保存できない
- **未来への蓄積**: 本システムが稼働し、定期的にデータを取得し続けることで、「〇年〇月〇日時点での事業概要はAであった」「〇年〇月〇日からはBに変更された」という**未来に向けた履歴の蓄積は可能**である。
- **過去への遡及不可**: 一方で、`yfinance`（および元データである Yahoo Finance）の API は、基本的に**「現在の最新のプロフィール情報」しか返さない**。
  - そのため、本システムを今日導入した場合、「1年前の事業概要がどうであったか」を API から遡って取得することは不可能である。

### 3.2 専門家（データエンジニア・金融アナリスト）の視点
この分野の専門家であれば、この制約に対して以下のように考える：
1. **「データは今日から集め始めるしかない」**: 過去の定性データのヒストリカルデータを提供している商用ベンダー（Refinitiv や Bloomberg 等）を利用しない限り、無料/格安のスクレイピングや API で過去の事業内容の変遷を遡ることはできない。
2. **「自社での蓄積（SCD）が競争優位になる」**: だからこそ、今日から SCD Type 2 で履歴を自前で蓄積し始めること自体に、将来的な価値（データアセットとしての価値）が生まれる。

## 4. データ保存方針
- **定性情報**: `data/profiles/{ticker}.json` にリスト形式で履歴を保存。最新のスナップショットは DuckDB の `info` テーブルにも格納。
- **財務諸表**: DuckDB の `financials`, `balance_sheet`, `cashflow` テーブルに格納。
- **株価**: DuckDB の `prices` テーブルに格納。
