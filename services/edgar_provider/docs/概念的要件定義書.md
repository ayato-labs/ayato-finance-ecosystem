# EDGAR Provider 概念的要件定義書 (Architectural Philosophy)

## 1. システムの本質的役割
本システムは、米国証券取引委員会（SEC）の EDGAR データベースとローカル分析環境を繋ぐ「高信頼・高速なデータ・ゲートウェイ」である。米国市場における膨大な財務データ（XBRL）およびテキスト情報（Narratives）を効率的に取得・構造化し、クオンツ分析や AI による定性分析に最適な状態で提供することに特化する。

**前提とする使用用途**:
日本市場データ（J-Quants/EDINET）と同様、**中長期投資・ファンダメンタル分析**を主目的とする。数万社に及ぶ米国上場企業の歴史的な財務数値の推移、および「Risk Factors」や「MD&A」といった重要な記述情報を、言語の壁を超えて機械可読な形式で蓄積・提供する。

## 2. 採用した方針とその理由 (What & Why)

### 2.1 DuckDB + Zstd による高度な圧縮と高速検索の両立
- **方針**: 数値データは DuckDB に格納し、テキストデータは Zstandard (zstd) で圧縮して BLOB として保存する。
- **理由**: 米国企業の財務事実は数千万件に達するため、列指向の DuckDB による集計の高速化が不可欠である。一方で、Narratives（記述情報）は非常にサイズが大きいため、圧縮なしではディスク容量を圧迫する。zstd を採用することで、高い圧縮率を維持しつつ、分析時にオンメモリで高速に展開可能な構造を実現した。

### 2.2 `edgartools` の戦略的採用
- **方針**: SEC API を直接叩くコードを自前で実装せず、実績のある Python ライブラリ `edgartools` をコアエンジンとして採用する。
- **理由**: SEC のデータ構造（XBRL, Bulk JSON）は非常に複雑であり、レートリミットや User-Agent の厳格な管理が必要である。`edgartools` はこれらの低レイヤーな制御や、複雑な XBRL のパース処理を高度に抽象化しており、本プロバイダーは「データの構造化と永続化」という上位の責務に集中できるため。

### 2.3 シャーディング（Facts / Narratives）によるデータ分離
- **方針**: 財務数値（Facts）と記述情報（Narratives）を別々の DuckDB ファイル（シャード）に分離して管理する。
- **理由**: Facts は頻繁に集計・検索が行われるが、Narratives は AI による抽出時など特定のワークフローでのみ参照される。これらを分離することで、一方のデータベース破損リスクが他方に波及するのを防ぎ、バックアップやスケーリング（年次ごとの分割など）を容易にするため。

### 2.4 データ・ハードニング（クランプ処理）の導入
- **方針**: インジェスト時に、会計年度や数値の異常値を厳格にバリデーションし、安全な範囲内にクランプ（固定）する。
- **理由**: SEC のデータには、稀に「20222年」といった入力ミスや、極端な浮動小数点数の異常値が含まれる。これらはデータベースの制約（SMALLINT 等）に違反し、インジェスト全体を停止させる原因となる。システム境界で「実務的にあり得ない値」を補正することで、パイプラインの完走を最優先するため。

---

### 2.5 解析・書き込み分離（Producer-Consumer）による安定化
- **方針**: バルクインジェスト時、データのパース（並列処理）とデータベースへの書き込み（単一スレッド・キュー経由）を完全に分離する。
- **理由**: DuckDB のようなシングルライター（書き込みは一人だけ）の DB において、多スレッドからの同時書き込みはデッドロックやクラッシュ（Segfault）の主因となる。書き込みを直列化し、キューによるバックプレッシャー制御を行うことで、リソースを限界まで使いつつ、決して止まらないパイプラインを実現するため。

### 2.6 RAM・CPUリソースの動的適応（Auto-Tuning）
- **方針**: メモリ上限（memory_limit）やスレッド数をハードコードせず、実行マシンのスペックを検知して動的に 70% 程度の最適値を割り当てる。
- **理由**: Edgar のデータ量は実行環境によってメモリ不足（OOM）を引き起こす可能性がある一方、高性能な環境ではより多くのリソースを活用して高速化すべきであるため。環境に依存しない堅牢性と、ハードウェア性能を最大限に引き出す柔軟性を両立するため。

## 3. 採用しなかった方針とその理由 (What Not & Why Not)

### 3.1 全ての SEC フォーム（Form 4, 8-K 等）の網羅
- **方針**: 現時点では 10-K（年次報告書）および 10-Q（四半期報告書）にターゲットを絞り、Form 4（役員売買）や 8-K（臨時報告）などの全取得は見送る。
- **理由**: 本システムの主眼は「企業の長期的本質価値」の算定にあり、まずは財務諸表と主要な記述情報の整備が最優先であるため。全てのフォームを対象にすると、データ量が指数関数的に増加し、ストレージコストと処理の複雑さが分析上のメリットを上回ると判断した。

### 3.2 生の XBRL（XML）データの直接保存
- **方針**: 生の XBRL ファイルをそのまま保存せず、必ず標準化されたコントラクト（Pydantic）に変換して保存する。
- **理由**: XBRL は階層構造が複雑すぎて直接的な分析（SQL 等）に向かない。また、タクソノミの違いを吸収しないまま保存すると、将来的な横断分析が不可能になる。インジェスト時に「意味のある単位」に正規化することで、分析効率を最大化するため。

### 3.3 リアルタイム・アラート機能の搭載
- **方針**: 提出直後のプッシュ通知やリアルタイム・スクレイピングは行わない。
- **理由**: 米国市場の開示は日本時間の深夜から早朝にかけて行われることが多い。本プロバイダーは「翌朝の分析フェーズ」に備えてデータを完璧に整えることに価値を置いており、数分を争うトレード用のリアルタイム性は、エコシステム内の他サービス（Reporter 等）に委ねるべき設計境界であるため。

### 3.4 複数マシンからの同時書き込み
- **方針**: クラウド型分散 DB（PostgreSQL 等）は採用せず、ローカル完結の DuckDB を維持する。
- **理由**: 「Local-First with External Fallback」の哲学に基づき、ネットワーク遅延や認証コストなしに分析を行える環境を最優先した。書き込みプロセスを 1 つに絞ることで、ファイルロックやコンフリクトの問題を回避し、シンプルなアーキテクチャを維持するため。

### 3.5 財務数値の精度削減（Float32 への変換）
- **方針**: ストレージ効率向上のために数値データを float32（単精度）に落とすことはせず、float64（倍精度）を維持する。
- **理由**: 数兆ドル規模の財務数値や億単位の株式数を扱う際、float32 では有効桁数が不足し、丸め誤差が発生するリスクがある。財務データの信頼性はシステムの生命線であり、容量の節約よりも計算の正確性を絶対的に優先すべきであるため。
