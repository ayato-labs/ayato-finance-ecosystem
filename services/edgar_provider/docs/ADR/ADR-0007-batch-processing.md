# ADR-0007: バッチ処理の導入

## ステータス

承認済み

## 概要

提出書類のDB書き込みを1件ごとの逐次処理から、バッチ処理に変更する。

## 背景

現在のシステムは、各提出書類を処理するたびにDuckDBに書き込みを行っている。この方式には以下の問題がある：

1. **ストレージ寿命**: フラッシュストレージの場合、書き込みサイクルの消費が大きい
2. **パフォーマンス**: 各書き込みごとにI/Oオーバーヘッドが発生
3. **トランザクションオーバーヘッド**: 各書き込みにコミット処理が必要

## 決定事項

1. **バッチ処理の導入**: 複数の書き込みをまとめて実行する
2. **バッチサイズ**: 環境変数 `BATCH_SIZE` で設定可能（デフォルト: 10件）
3. **バッファリング**: 処理結果をメモリにバッファリングし、バッチサイズに達したら一括書き込み
4. **フォールバック**: 処理終了時に残りのバッファを一括書き込み

## 利点

1. **ストレージ寿命の延伸**: 書き込みサイクルの削減により、ストレージ寿命が2-3倍延びる可能性
2. **パフォーマンス向上**: I/Oオーバーヘッドの削減により、処理速度が向上
3. **トランザクション効率**: コミット回数の削減により、トランザクションオーバーヘッドを削減
4. **柔軟性**: 環境変数でバッチサイズを調整可能

## 欠点

1. **メモリ使用量**: バッファリングにより、メモリ使用量が増加
2. **エラー復旧**: バッチ処理中のエラー発生時、一部のデータが失われる可能性

## 実装詳細

### storage.py

```python
def save_filings_batch(self, filings_data: list[tuple[dict, dict]]) -> int:
    """複数の提出書類を一括で保存します。"""
    
def save_facts_batch(self, facts_data: list[tuple[str, str, pd.DataFrame]]) -> int:
    """複数のファクトを一括で保存します。"""
```

### pipeline.py

```python
BATCH_SIZE = int(os.getenv("BATCH_SIZE", "10"))

# バッファリング
filings_buffer: list[tuple[dict, dict]] = []
facts_buffer: list[tuple[str, str, any]] = []

# バッチサイズに達したら一括書き込み
if len(filings_buffer) >= BATCH_SIZE:
    storage.save_filings_batch(filings_buffer)
    filings_buffer.clear()
```

## 専門家レビュー

1. **データベースエンジニア**: バッチインサートはDuckDBの列指向ストレージに最適
2. **パフォーマンススペシャリスト**: ネットワーク待ち時間とDB書き込みの並列化が可能
3. **ストレージスペシャリスト**: WAF（Write Amplification Factor）の削減が見込める
4. **システムアーキテクト**: アトミックな書き込みにより、データ整合性が向上
5. **DevOpsエンジニア**: ログ量の削減とモニタリングの容易化

## 環境変数

| 変数名 | 説明 | デフォルト値 |
|--------|------|--------------|
| `BATCH_SIZE` | バッチ処理のバッチサイズ | 10 |
