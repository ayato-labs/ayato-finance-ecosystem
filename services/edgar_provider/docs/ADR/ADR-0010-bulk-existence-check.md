# ADR-0010: バルク一括存在チェックによる同期パイプライン高速化

## ステータス

承認済み

## 概要

SEC Daily Index および特定ティッカー同期処理において、書類ごとに個別発行していたデータベース存在チェック（`filing_exists` / `facts_exist`）を、一括照会（`filing_exists_batch` / `facts_exist_batch`）へ変更する。これにより、クエリオーバーヘッド（2N回 → 2回）および不要な個別ログ出力を削減し、同期パイプラインのレスポンス性能を飛躍的に向上させる。

## 背景

`sync_recent_us_filings` や `process_us_tickers` において、提出書類（10-K, 10-Q）がすでにDBに登録済みかどうかの確認をループ内で各件数ごとに `storage.filing_exists(acc_no)` および `storage.facts_exist(acc_no)` を個別に実行していた。

この設計には以下の課題が存在した：
1. **DBクエリオーバーヘッド**: 対象書類が N 件ある場合、最大 2N 回の個別の SELECT クエリが発生していた。
2. **ログの氾濫とI/O遅延**: 過去データ同期時に数百件〜数万件の「Skipping (already synced)」ログが1件ずつ出力され、コンソールおよびファイルI/Oの大きなオーバーヘッドとなっていた。

## 決定事項

1. **バルク一括判定 (`filing_exists_batch` / `facts_exist_batch`) への全面移行**
   - インデックス取得後、対象となる全 `accession_number` のリストを作成し、一括でSQLの `IN (...)` クエリを発行して登録済みセット（`Set[str]`）を取得する。
2. **$O(1)$ メモリ判定への変更**
   - ループ内では、取得したハッシュセットを利用して即座に重複判定を実施する。
3. **スキップログの集約**
   - 個別の件数ごとの INFO ログ出力をスキップし、日ごと・ティッカーごとのサマリーログ（件数および上位数件の要約）1行のみの出力にまとめる。

## 利点

1. **同期処理の超高速化**: クエリ回数が数千回から数回に削減され、I/O待ち時間が大幅に短縮される。
2. **可読性の高いログ出力**: 処理状況の全体像（処理数、スキップ数）が簡潔な要約ログとして記録される。
