# EDGARデータパイプライン：ストレージ効率向上の工夫

EDGARデータのインジェストパイプラインにおいて、パフォーマンスの最大化とストレージ使用量の最小化を両立するために実施した技術的な工夫をまとめます。

## 1. スタースキーマ（Star Schema）への正規化

従来のフラットなテーブル構造（1つのテーブルに全ての情報を保持）から、正規化されたスタースキーマへ移行しました。

### 構成
- **`filings` テーブル（Dimension/Metadata）**: 提出物単位の情報（ticker, cik, form, filed_date）を保持。
- **`company_facts` テーブル（Fact）**: 数値データ（label, value, unit, fy, fp）を保持。`accession_number` を外部キーとして使用。

### 効果
- **文字列データの重複排除**: `ticker`（例: "AAPL"）や `form`（例: "10-K"）といった文字列が、数万行のファクトごとに繰り返されるのを防ぎます。
- **結合（JOIN）の最適化**: メタデータがコンパクトになることで、特定の企業や日付範囲でのフィルタリングが高速化されます。

## 2. データ型の最適化（Type Hardening）

DuckDBのストレージ効率を最大化するため、汎用的な文字列型を排除し、厳密な数値型および日付型を導入しました。

| カラム名 | 変更前 (Legacy) | 変更後 (Optimized) | 理由 |
| :--- | :--- | :--- | :--- |
| `cik` | `VARCHAR` | `UINTEGER` | CIKは10桁の数字であり、数値として保持する方が遥かに効率的。 |
| `filed_date` | `VARCHAR` | `DATE` | DuckDBの内蔵日付型を使用することで、日付演算の高速化と圧縮率の向上を実現。 |
| `fiscal_year` | `INTEGER` | `SMALLINT` | 西暦（2024等）は2バイト（-32768〜32767）で十分収まるため。 |
| `value` | `DOUBLE` | `DOUBLE` | NaNや無限大（Inf）をパース時に `0.0` へクランプし、DBの安定性を向上。 |

## 3. インメモリ重複排除（In-Memory Deduplication）

データベースへの挿入前に、Pandasを使用してバッチ内での重複排除を実施しています。

- **Primary Keyの保護**: 同一の `(accession_number, label)` の組み合わせが同一トランザクションに含まれないよう、`drop_duplicates` を実行。
- **競合回避**: DuckDBの `INSERT OR REPLACE` 実行時に発生し得るセグメンテーション違反（特にインデックス更新時）を、メモリ上でのクリーンアップによって未然に防ぎます。

## 4. バルクインジェストの安定化戦略

大量データ（数千万行単位）のインジェスト時に、DuckDBの安定性を維持するための「枯れた技術」を組み合わせています。

- **セカンダリインデックスの動的制御**:
    - インジェスト開始前に `DROP INDEX` を実行。
    - 全データの挿入完了後に `CREATE INDEX` で一括構築。
    - これにより、1行ごとのインデックス更新負荷を排除し、インジェスト速度を数倍に高めるとともに、インデックス破損リスクを解消しました。
- **サブバッチ処理**:
    - 1トランザクションを5,000行単位の小規模なチャンクに分割。
    - メモリ使用量のスパイクを抑え、低スペックな環境でも安定して稼働するように設計されています。

## 5. ストレージ効率の期待値

この変更により、`facts.duckdb` のファイルサイズは、フラットな構造と比較して **約30%〜50% 削減** されると推定されます（特に文字列データの多い大規模データセットにおいて顕著）。
