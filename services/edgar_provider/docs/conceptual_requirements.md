# 概念的要件定義書 - EDGAR Provider

## 1. プロジェクトの目的
米国証券取引委員会（SEC）の提出書類（10-K, 10-Q等）から、**「定性情報（文章）」**と**「定量情報（財務数値）」**の両方を抽出・構造化し、統一された DuckDB データベースに保存することを目的とする。これにより、AIによるテキスト分析とデータ駆動型の数値分析を同一基盤上で行えるようにする。

## 2. 実装の方針（何を採用し、なぜそうするのか）

### 2.1. データ集約化（ADR-0001準拠）
- **方針**: データベースファイルをサービス内部ではなく、プロジェクトルートの `data/edgar/` に配置する。
- **理由**: 他の金融データサービス（J-Quants, EDINET等）と物理的に場所を揃えることで、DuckDB の `ATTACH` 機能を活用したクロスデータ分析を容易にするため。

### 2.2. 定性情報の抽出（HTML解析）
- **方針**: HTMLドキュメントを Markdown に変換した後、正規表現を用いて特定のセクション（Business, Risk Factors等）を切り出す。
- **理由**: SECのHTMLは構造が複雑だが、Markdown に一度平坦化することで、LLM（大規模言語モデル）への入力や全文検索が容易になるため。

### 2.3. 定量情報の抽出（edgartools の活用）
- **方針**: 自前での数値パースではなく、外部OSSの `edgartools` を使用して XBRL/Facts データを取得する。
- **理由**: 米国株の財務数値はタクソノミが膨大かつ複雑であり、成熟したライブラリに依存することで保守コストを抑え、正確性を担保するため。

### 2.4. ストレージ（DuckDB）
- **方針**: ファイルベースの DuckDB を採用し、複雑なデータは JSON 型カラムを活用して保存する。
- **理由**: 大規模なデータセットに対する集計クエリが高速であり、かつスキーマの変更（新しいセクションの追加など）に対して柔軟に対応できるため。

## 3. 非採用の方針（何をせず、なぜしないのか）

### 3.1. PDF形式の直接解析
- **方針**: PDFファイルをダウンロード・解析するロジックは実装しない。
- **理由**: PDFはレイアウト解析が極めて困難で情報の欠落が発生しやすいため。SECが提供する機械読取可能な HTML (iXBRL) および Facts JSON を正とする。

### 3.2. 常時接続型の RDBMS (PostgreSQL等) の直接利用
- **方針**: 本サービス単体で PostgreSQL 等への書き込みは行わない。
- **理由**: ローカル環境での分析効率とポータビリティを最優先するため。将来的なクラウド移行時は、環境変数で接続先を切り替える「抽象化レイヤー」での対応に留める。

### 3.3. リアルタイム・ストリーミング取得
- **方針**: 数秒単位のリアルタイム同期は実装せず、日次のバッチ同期とする。
- **理由**: SEC APIのレートリミット（10 req/sec）を遵守する必要があり、また決算書類というデータの性質上、日次更新で十分に分析要件を満たせるため。
