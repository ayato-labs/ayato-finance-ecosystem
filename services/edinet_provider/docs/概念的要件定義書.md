# 概念的要件定義書 (Conceptual Requirements Definition)

本ドキュメントは、EDINETデータプロバイダーにおける設計思想、技術選定の根拠、および「何を行い、何をあえて行わないか」という戦略的方針を定義するものである。

## 1. 核心的設計思想：Quad-Split アーキテクチャ

### 採用する方針
- **データベースの物理的分割 (Quad-Split)**
  - `Registry`, `Facts`, `Narratives`, `Master` の4つのDuckDBファイルに分割する。
  - **理由**: データ特性（更新頻度、データ量、圧縮効率）に応じた最適化を行うため。特にNarratives（テキストデータ）はZSTD圧縮を効かせることで、OLAP分析用のFactsとは異なるストレージ特性を持たせる。
- **シャーディング・プレフィックスの徹底**
  - SQLクエリ内で常に `registry_db.` 等のプレフィックスを明示的に使用する。
  - **理由**: 開発環境（インメモリ）と本番環境（物理ファイル）のSQL互換性を100%維持し、不透明な結合（Implicit Join）によるバグを排除するため。

### 採用しない方針
- **単一巨大データベースファイルへの統合**
  - **理由**: 特定のドメイン（例：テキスト抽出）の失敗が他のドメイン（例：財務数値）のデータ保全に波及するリスクを避けるため。

## 2. 並列解析と直列書き込み (Producer-Consumer パターン)

### 採用する方針
- **並列解析 (Parallel Extraction)**
  - ドキュメントの取得やXBRL/CSVデータのパース処理は、`ThreadPoolExecutor` を用いてマルチスレッドで並列に実行する。
  - **理由**: ネットワークI/O（EDINET APIからのダウンロード）とCPUバウンドな解析（ZIP解解凍、XMLパース等）を効率よく捌き、スループットを最大化するため。
- **キューによる直列保存 (Serialized DB Writes)**
  - 並列に解析された結果はインメモリのキュー（`queue.Queue`）に投げられ、単一の専用バックグラウンドスレッド（`DBWriterThread`）が順次 DuckDB へ書き込む。
  - **理由**: DuckDB はファイルベースのデータベースであり、複数スレッド/プロセスからの同時書き込み競合（Lock Contention / IO Error）に弱い。書き込み経路を単一化することで、安全かつ高速なバッチインサートを実現するため。
- **ライフサイクルの厳密な管理 (Thread Lifecycle Management)**
  - ループ処理などによる差分更新時、DB書き込みスレッドの起動（`start`）と停止・破棄（`stop`）をイテレーションごとに確実に実施する。
  - **理由**: スレッドの終了フラグや参照が残存することで、次回以降のイテレーションでスレッドが再起動せず、メモリ上のキューにデータが無限に溜まり続ける（OOMやフリーズを引き起こす）サイレントな不具合を防止するため。

### 採用しない方針
- **解析スレッドからの直接DB書き込み**
  - **理由**: トランザクションロックの奪い合いが発生し、全体のパフォーマンス低下やデッドロックを招くため。

## 3. 弾力性 (Resilience) とエラーハンドリング

### 採用する方針
- **部分成功 (Partial Success) の許容とバッチ分離**
  - 1つのレコードが制約違反（NOT NULL違反など）を起こしても、バッチ全体をロールバックせず、正常なレコードのみを保存し、異常レコードを `error.log` に隔離する。
  - **理由**: EDINETの生データには不可避な不整合が含まれるため、完璧主義的なトランザクション管理は同期の停止を招く。
- **構造化ログ (JSON) による完全な追跡性**
  - Loguruを使用し、全てのログをJSON形式で出力。
  - **理由**: 大規模データ処理において、どの `session_id` や `doc_id` で問題が発生したかを機械的に高速検索可能にするため。
- **例外の「握りつぶし」の厳禁**
  - `except: pass` や原因を明示しない `except: logger.warning` を禁止し、必ず例外のコンテキストを記録する。

### 採用しない方針
- **全件保存・全件エラーの二者択一**
  - **理由**: 数万件のバッチ処理において、1件のデータ不備で数時間の処理を無にするのは非効率的であるため。

## 4. 並列処理とコンテキスト伝播

### 採用する方針
- **TraceID のスレッド間伝播**
  - `ContextVar` とラッパー関数 `with_context` を使用し、メインスレッドの TraceID を `ThreadPoolExecutor` のワーカースレッドへ強制的に引き継ぐ。
  - **理由**: 非同期・並列処理下において、ログの相関関係を見失わないようにするため。

### 採用しない方針
- **asyncio による I/O 待ち制御**
  - **理由**: CPUバウンドなパース処理とI/OバウンドなAPI取得が混在しており、実装の複雑化を避けるため、現時点では `ThreadPoolExecutor` によるスレッド並列を優先する。

## 5. 開発・品質管理

### 採用する方針
- **静的解析の「自動修復」不使用**
  - Ruffを使用するが、`--fix` は使用せず、人間（または高度なエージェント）が意図を持って修正する。
  - **理由**: 自動修復による意図しないロジック変更や、破壊的なリファクタリングを防止するため。
- **100文字制限の採用**
  - **理由**: 現代的なディスプレイ環境と、ネストの深い例外処理を読みやすく維持するため。

### 採用しない方針
- **過度なモックを使用したテスト**
  - **理由**: DBの挙動（DuckDBのSQL仕様）そのものがバグの温床になりやすいため、インメモリDBを使用した統合テストを重視する。

## 6. ストレージ最適化と型ガバナンス (Storage & Type Governance)

### 採用する方針
- **XBRLタグ名・各種コード類への VARCHAR 採用**
  - `section_name` (XBRLタグ), `form_code`, `doc_type_code`, `unit` などの、外部要因で増減しうる項目には ENUM ではなく `VARCHAR` を使用する。
  - **理由**: これらのコード体系は EDINET 側の仕様変更や新規事象の発生（例：新しい書類形式の追加）により、運用中に未知の値が出現する不確実性がある。ENUM は DuckDB 内部で固定のインデックスとして管理されるため、未知の値の出現が `Conversion Error` を引き起こし、システム全体の同期停止（Resilience の喪失）を招く。ストレージ効率よりも、長期的な無停止運用（堅牢性）を最優先する。
- **Native ZSTD 圧縮の活用**
  - 大規模なテキストデータ（`content_md`）には DuckDB の `USING COMPRESSION ZSTD` を明示的に指定する。
  - **理由**: Python 側での圧縮管理負荷を軽減し、DB エンジンによる効率的な透過的圧縮を利用するため。

## 7. リソース・ガバナンス (Resource & Memory Governance)

### 採用する方針
- **動的スロットリングによる OOM 回避**
  - システム全体のメモリ使用率が **95%** を超えた場合、新規タスクの投入を一時停止し、既存タスクの完了とメモリ解放を待機する。
  - **理由**: バッチ処理中の予期せぬ RAM 肥大化によるシステム全体のハングアップやプロセス強制終了を防止し、低リソース環境下でも確実に完走させるため。
- **DuckDB メモリ制限と Spilling to disk の活用**
  - DuckDB のメモリ制限をシステム RAM の 30% に設定し、`temp_directory` を明示的に指定する。
  - **理由**: オンメモリで処理しきれない大規模データ（巨大な XBRL 解析結果等）を安全にストレージ（ディスク）へ逃がす（Spilling）ことで、RAM 不足によるクラッシュを回避するため。
- **チャンク実行と明示的 GC (Garbage Collection)**
  - 全件一括実行ではなく、Worker 数に基づいたチャンク単位での実行を行い、チャンクごとの `gc.collect()` を実行する。
  - **理由**: Python のメモリ管理を補助し、特に大規模なテキストオブジェクトを早期に解放してメモリリークのような挙動を抑制するため。

### 採用しない方針
- **動的生成された ENUM による全項目の厳密管理**
  - **理由**: XBRL タグは業界や年度によって新規追加・変更される不確実な集合であり、これを静的な ENUM で拘束することは同期エンジンの脆弱性に直結するため。
