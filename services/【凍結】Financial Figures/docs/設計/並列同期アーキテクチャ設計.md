# 並列同期アーキテクチャ設計 (マルチソース対応)

## 1. 概要
従来の `BatchSyncService` は、全てのデータベース書き込み（米国、日本、EDINET）に対して単一の `db_queue` と `DBWriter` スレッドを使用していました。DuckDB は「1つのデータベースファイルに対して単一のライター」という制限がありますが、本プロジェクトのアーキテクチャでは物理的に分離されたファイル（`us.duckdb`, `jp.duckdb`, `edinet.duckdb`）を使用しています。そのため、全ての市場に対してグローバルな書き込みロックを強制することは、人工的なボトルネックとなっていました。

本設計では、各市場に対して独立したキューとライタースレッドを確立し、真の並列同期を実現すると同時に、統一された AI マッピングキューを維持するリファクタリングの詳細を定義します。

## 2. アーキテクチャの変更

### 2.1 キューの分離
- **変更前:** 1つの `db_queue`
- **変更後:** 
  - `us_db_queue`: `us_db_worker` が消費
  - `jp_db_queue`: `jp_db_worker` が消費
  - `edinet_db_queue`: `edinet_db_worker` が消費
  - `audit_db_queue`: `audit_worker` が消費（市場DBの書き込み中に監査ログでロックが発生するのを避けるため）

### 2.2 タグ発見（Tag Discovery）のオフロード
- **現状のボトルネック:** `_queue_unmapped_tags` が `_process_db_task` 内で同期的に実行されており、1銘柄あたり約0.24秒間、データベースの取り込みが一時停止しています。
- **改善案:** タグ発見処理を専用の `TagDiscoveryWorker` に移動するか、フェッチャースレッドがデータを取得した直後に非同期でプッシュするように変更し、高速な取り込みループから切り離します。

### 2.3 プロバイダーの隔離 (Provider Isolation)
- **現状:** `EDINETSyncWorker` などがメインスレッドをブロックし、同期中に AI マッピングがインラインで実行されています。
- **改善案:** 各プロバイダーを独立したワーカーとして統合します。各フェッチャーは、財務データをそれぞれの市場用 DB キューに、未知のタグを共通の `ai_queue` にプッシュする責務のみを負います。

## 3. 期待される成果
- **スループットの向上:** 米国市場や EDINET の同期が、J-Quants API の強制的な待機時間（12.5秒）に縛られることなく、大幅に高速化されます。
- **リソースの有効活用:** ネットワーク I/O、DB I/O、および AI マッピングが独立したパイプラインで並行して動作するため、CPU コアをより効率的に利用できます。
- **安定性:** データベース間のロック競合（例：日本市場のデータがキューで待機している間に米国市場の DB がロックされる等）が完全に解消されます。
