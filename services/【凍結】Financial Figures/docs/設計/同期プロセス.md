# 同期プロセス

本ドキュメントでは、データの差分更新ロジック、プロバイダー隔離パターン、およびバッチ実行のスケジューリング方針について定義する。

---

## 1. プロバイダーの隔離と疎結合化方針 (Provider Isolation Pattern)

本システムは、データソース（EDINET, SEC-EDGAR, J-Quants）ごとにソースコードおよび実行プロセスを完全に独立させる**「プロバイダー隔離パターン」**を採用する。

| 決定 | 内容 | 理由 |
|---|---|---|
| **物理的隔離** | `src/providers/` 配下にソースごとの独立したパッケージを作成。 | データソース固有のロジックが他の市場へ混入（依存）することを防ぐ。 |
| **プロセス分離** | `scripts/` にソースごとの単独起動スクリプトを用意。 | 1つのソースのクラッシュが全同期を止めない「障害の局所化」を実現。 |
| **独立レート制限** | 各ワーカーが独立して待機（Sleep）制御を行う。 | 複数の市場を同時に、各 API の限界速度で同期可能にする。 |

**隔離を導入する理由:**
1. **保守性の向上**: EDINET の仕様変更（CSV 形式の変更等）が SEC-EDGAR のコードに影響を与えることがなくなり、変更時の影響範囲が明確になる。
2. **エラー耐性**: 特定の API がメンテナンスやレート制限で停止しても、他の市場の同期は継続できる。
3. **運用のスケーラビリティ**: 過去 10 年分のバックフィルなど重い処理を行う際、独立したターミナルで特定のワーカーだけを複数並列で動かすなどの柔軟な運用が可能になる。

## 2. 差分更新ロジックレイヤー

本システムの核心概念。毎回全量再取得しないことで、API レート制限・実行時間・コストを最小化する。

### 2.1 差分判定・AI マッピングの方式 (Hybrid)

| 決定 | 内容 |
|---|---|
| **Native Storage** | SEC EDGAR 等の生タグ(`NetIncomeLoss` 等)をそのまま物理 DB に保存。 |
| **Common Interface (Logical)** | 共通項目(売上高、純利益等)については、AI が「この生タグはどの標準項目に対応するか」を判定し、マッピング・ビューを生成。 |
| **Mapping Cache** | AI の推論結果は監査 DB の `mapping_audit` に永続化し、分析時の変換を高速化・固定化する。 |
| **Task-level Retry** | 書き込み失敗時、タスクをキューの最後尾に戻すことで、一時的な DB 負荷やロックによるデータ欠落を完全に防止する。 |
| **docID / CIK ポリング** | 提出書類の一覧を監視し、未登録分のみを取得する。 |

### 2.2 差分更新で使わない方式

| 非採用 | 理由 |
|---|---|
| 全量削除 → 全量再挿入 (TRUNCATE & INSERT) | API 負荷が高くレート制限に抵触する |
| ハッシュ比較による行レベル変更検出 | 財務数値の訂正(修正開示)への対応として将来検討するが、初期実装では過剰 |

---

## 3. スケジューリング・バッチ実行レイヤー

| 決定 | 内容 | 理由 |
|---|---|---|
| **使う** | `APScheduler`(Python内スケジューラ) または OS の `cron` | シンプルなローカル定期実行に最適。外部依存なし |
| **使わない** | Celery + Redis / RabbitMQ | ローカル単一プロセスに対してキューブローカーは過剰 |
| **使わない** | Airflow / Prefect / Dagster | ワークフローオーケストレーションはスケールに対して過剰 |
