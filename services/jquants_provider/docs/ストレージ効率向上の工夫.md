# J-Quants Provider: ストレージ効率向上のための設計と工夫

本プロジェクトでは、数百万行を超える金融データの長期蓄積に耐えうる、高効率かつメンテナンス性の高いデータレイク構造を採用しています。本ドキュメントでは、ストレージ効率を最大化するために導入された技術的工夫を解説します。

## 1. 基礎基盤：DuckDB カラムナーストレージ

基盤となるデータベースに **DuckDB** を採用することで、標準的な RDBMS と比較して圧倒的な圧縮率と検索速度を両立しています。

- **列指向（Columnar）保存**: 同一列のデータ（株価の数値など）が連続して配置されるため、データの類似性が高く、圧縮効率が極めて高くなります。
- **自動軽量圧縮**:
    - **Bit-packing**: 数値の大きさに合わせてビット単位で動的に容量を最適化します。
    - **Dictionary Encoding**: 銘柄コード（Code）などの重複が多い文字列を辞書化して最小容量で保持します。

## 2. 実装された最適化施策：VACUUM（領域の再構築）

データの大量投入や削除を繰り返すと、データベースファイル内部にフラグメンテーション（断片化）が発生します。これを解消するためにメンテナンス機能を実装しました。

- **CHECKPOINT**: メモリ上の書き込みログをすべて物理ファイルへフラッシュし、データの整合性を担保します。
- **VACUUM**: ファイル内の未使用領域をOSに返還し、物理的なファイルサイズを最小化します。
    - **自動実行**: `full_backfill.bat` の末尾に組み込まれており、同期完了後に自動で最適化が行われます。
    - **手動実行**: `python main.py --optimize` で任意のタイミングで実行可能です。

## 3. アーカイブ戦略：Parquet + ZSTD の活用

「枯れた技術」でありながら業界標準である **Apache Parquet** 形式へのエクスポート機能を搭載しています。

- **Zstandard (ZSTD) 圧縮**: 高速な展開と極めて高い圧縮率を両立するアルゴリズムを採用。
- **不変データの分離**: 過去数年分の「もう更新されない」歴史データを Parquet に切り出すことで、`.duckdb` ファイルを常に軽量（Hot Dataのみ）に保つことが可能です。
- **サイドエフェクトの排除**: DuckDB は Parquet ファイルをネイティブテーブルと同様に直接クエリできるため、アーカイブ化しても検索ロジックを変更する必要がありません。

## 4. 運用上のメリット

- **データ不整合の防止**: Pydantic コントラクトでの型強制（float）により、DuckDB の型推論バグを回避し、常に最適なバイナリ表現で保存されます。
- **ゼロコスト・スケーラビリティ**: アーカイブ化と `VACUUM` の組み合わせにより、家庭用PCのディスク容量でも数十年分の全市場データを保持し続けることが可能です。
